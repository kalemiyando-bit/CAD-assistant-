name: Design assistant scope
description: The intended scope and software-selection behavior for the engineering design assistant.
---

This project is a system for helping the user build engineering designs through Replit Agent and other Replit agents. It is not a web app or a standalone Python app, and it is not a system for copying the appearance of a product from a reference. The shaft is only a workflow example. Autodesk Fusion is the planned primary CAD target, while the system should continue supporting multiple CAD, drafting, electronics, and related tools.

The system is a conversational, Replit-first workflow that uses Replit's Agent environment and project Skills to help the user with engineering and CAD design. It is not intended to be a conventional web app or a standalone Python application. Python scripts may serve as bridges or helpers for CAD software, but they are not the product.

The user agreed to an iterative manager/worker process: Replit Agent and the user establish the task, then Replit Agent prepares a focused Gemini handoff, reviews the result, prepares follow-up instructions as needed, and takes over if Gemini cannot meet requirements. A local CLI worker now calls Gemini with the user's key from Replit Secrets and returns a validated preliminary Fusion v1 model spec. There is no public API endpoint or UI.

To reduce repeated context and test cost, start from `replit.md`, read only files relevant to the current task, and avoid routine full-suite runs. For CAD outputs, check loading in the target application first; if it fails, run focused diagnostics. Keep contract-required safety or release checks.

Ask which software the user is using for each design task, and ask for its version or operating system when compatibility or instructions depend on them. Make clear whether the agent can operate that software directly or can only provide compatible files, scripts, or instructions.

For early system testing, the user wants to describe a design conversationally, receive a clearly labeled preliminary draft, and continue developing it in Fusion. The user usually turns 2D drawings into 3D models, but the purpose can vary by job. Test one simple part at a time: start with its 2D drawing, then its 3D model, before expanding to other parts, assemblies, safety/control design, and PCB work. Before making a 2D deliverable, ask whether it is for building 3D geometry, documentation, or both; use separate outputs, and keep borders and annotation geometry out of model-building sketches. Do not block these tests on manufacturing-release completeness; keep assumptions and unverified limits explicit. Document exact Skills, scripts, and checks so other agents can reuse methods already tested.

As of 2026-11-08, the user reports that tests passed and the shaft example can produce both a 2D drawing and a 3D model. The exact Fusion-side checks included in that report are not yet recorded; treat it as the current user-confirmed capability, but do not infer archive-reopen verification or manufacturing readiness. The user prefers their Gemini API credentials stored in this project's Replit Secrets. The user says the current milestone is testing the Gemini integrations to confirm they behave as expected. See `AI_COMPUTE_SUPPLEMENT_DISCUSSION.md` for the integration status and agreed handoff.

**Why:** The user emphasized that CAD Assistant exists to help them and other Replit agents build their own engineering designs; the shaft is only an example. They approved the Replit-manager/Gemini-worker handoff and asked to reduce broad context review and routine test runs. They chose their own Google API billing and now identify Gemini integration testing as the active milestone. For the Wheel Drive Bench Demonstrator, they clarified on 2026-11-08 that this is a simple proof of concept, authorized sensible preliminary choices because exact specifications are unavailable, and asked for individual parts before the assembly. They also specified GAS/BRAKE tap-and-hold speed controls, a separate handbrake/emergency stop, wheel-speed measurement, and no reverse. On 2026-11-08 they further requested 3D parts only for now, with no 2D drawings or profiles, and showed their previously tested Fusion `generate_fusion_model` 1.1.0 add-in, asking to reuse it for new model files. The CLI avoids exposing the key through a public, unauthenticated billable endpoint. Exact Fusion-side checks for the shaft remain undocumented; the worker's model-spec output is not a Fusion import or engineering validation.

**How to apply:** Include a software-selection question in every design intake. For 2D work, ask the modeling-versus-documentation question before generation and create separate outputs when both are needed. Keep software-specific handoffs and tool-capability checks separate from the core, platform-neutral design brief. Treat the shaft's 2D/3D capability as user-confirmed while recording exact checks before making stronger validation claims. For this wheel-drive proof of concept, keep each part simple and preliminary, label chosen dimensions and control rates as assumptions, honor the no-reverse requirement, and provide 3D-only outputs unless the user asks to resume 2D work. The user wants all planned parts created before the combined verification phase; keep parts separate while modeling, then review them before making an assembly. The user knows how to run the existing Fusion add-in; prepare the next part's JSON and handoff without repeating installation guidance unless asked. For supported parts, use the same add-in; do not require installing a new one for each part. Include or replace the add-in only for a fresh setup or when its supported capabilities need a deliberate update. Use the local Gemini CLI only for a user-approved, supported one-part Fusion model-spec draft; inspect its assumptions and validation output, then let the user review it in Fusion. Keep credentials server-side and do not add a public route or UI unless a specific need is agreed.
